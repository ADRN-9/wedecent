# WeDecent v0.4 Plan

## Theme

v0.4 begins the transition from a technically validated remote-terminal system into a user-facing multi-transport connectivity platform.

The two primary goals are:

1. establish the mesh-routing foundation
2. begin the consumer application architecture

v0.3 remains the compatibility and security baseline.

## Product direction

The long-term WeDecent product family is expected to include a website plus Windows, Linux, macOS, Android, and iOS applications.

All interfaces should share one networking and security core. The existing Go implementation remains the core. Platform UIs must not independently implement identity, authorization, relay protocols, routing, or cryptography.

## Architectural shape

```text
                  WeDecent Web
                       |
                Control plane
                       |
          +------------+------------+
          |            |            |
       Windows       Linux        macOS
          |            |            |
          +------ Local Core API ---+
                       |
                 WeDecent Go Core
                       |
        +--------------+--------------+
        |              |              |
       LAN          Internet       Bluetooth
        |              |              |
        +--------- Mesh Router -------+
                       |
                Secure Sessions
```

Mobile applications will use the same core model later.

## v0.4 milestones

### v0.4.1 — Mesh foundation

Deliverables:

- architecture documentation
- Peer representation
- Transport abstraction
- Link abstraction
- RouteHop and Route
- RouterPolicy
- RoutePlanner foundation
- unit tests

Constraint: no existing production connection path changes.

### v0.4.2 — Direct LAN

Deliverables:

- trusted-node LAN discovery
- authenticated neighbor identification
- direct protected connection
- direct-vs-relay selection
- timeout and fallback behavior
- Windows LAN tests

Success condition: two trusted machines on the same LAN connect directly without requiring their session data to traverse the Internet relay.

The existing relay remains the fallback.

### v0.4.3 — Trusted one-hop routing

Deliverables: `A -> B -> C`, where B forwards an authorized WeDecent session.

Required controls include router opt-in, trusted identity validation, route authorization, route expiry, loop prevention, connection limits, bandwidth limits, safe logging, disconnect propagation, and fallback.

Success condition: A reaches C through trusted router B even though A cannot directly reach C.

### v0.4.4 — Local Core API

Define a versioned API between UI applications and the Go core.

Initial operations: status, sign in/out, list devices, device details, connect/disconnect, transport status, route status, router policy, and router statistics.

Private keys are never returned through this API.

### v0.4.5 — Windows GUI prototype

Initial screens:

- Welcome / Sign In
- My Devices
- This Device
- Connect
- Network Participation / Settings

Primary onboarding objective:

```text
download
install
sign in
device becomes available
connect to another device
```

A normal user should not need PowerShell.

### v0.4.6 — Windows productization

Deliverables:

- signed executable
- signed installer
- straightforward uninstall
- automatic or assisted updates
- stable download UX
- website download page
- user documentation
- security/privacy explanation

## v0.5 direction

Expected focus:

- Linux packages
- Linux router/node support
- multi-hop routing
- route health
- bandwidth policies
- early Bluetooth transport work

## Later platforms

Suggested sequence:

```text
Windows
Linux
macOS
Android
iOS
```

Android and iOS should initially focus on client/controller functionality. Continuous routing on mobile must account for operating-system background-execution restrictions.

## Website direction

`wedecent.com` should provide product explanation, downloads, documentation, the security model, and network participation information.

A later authenticated `app.wedecent.com` surface can provide account management, devices, organizations, trust relationships, and router/node visibility.

## UX positioning

Lead with the user benefit rather than implementation terminology.

```text
Access your computers from anywhere.
No public IP.
No port forwarding.
Protected connections.
```

Later network participation can be introduced as:

```text
Help make WeDecent faster and more resilient.
Your node forwards protected traffic.
You control when it participates.
```

Network participation must always be explicit opt-in.

## Security gates for mesh milestones

Before merging a networking milestone:

- `go test ./...`
- `go vet ./...`
- Windows cross-build/test
- `git diff --check`
- protocol tests
- authorization-negative tests
- replay tests where applicable
- malformed-route tests
- failure/fallback tests
- existing v0.3 path regression tests

Any feature that changes endpoint confidentiality, authorization semantics, or private-key handling requires explicit security review before release.

## Development principle

Do not replace the proven path while building the new one.

```text
existing v0.3 path
        +
new optional mesh paths
        +
route planner
```

until the mesh implementation has accumulated equivalent validation.

Start with data structures/interfaces and unit tests. No production connection path should use them until their boundaries are reviewed.
