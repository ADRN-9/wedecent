# Native Windows client trust onboarding

Native Windows clients keep an independent WeDecent identity and trust store under the Windows user's client state directory. Account credentials remain protected with CurrentUser DPAPI; the trust store contains device identity pins and locators, not account bearer credentials.

## Relay pairing

Worker v8 requires every client WebSocket stream to carry both a valid `wdt2` endpoint proof and a short-lived account connection grant. `wd pair --web-relay ...` therefore acquires a fresh grant from the authenticated account session before opening the relay stream, just like `wd connect`.

The account grant is relay admission only. Pairing still independently requires:

- the expected target device fingerprint;
- the target device ID;
- a high-entropy single-use pairing secret generated by the agent;
- the client's Ed25519 identity and the agent's inner TLS identity.

The pairing secret is prompted without echo on Windows through `CONIN$`; putting it in `WEDECENT_PAIRING_SECRET` remains available only for controlled automation.

## Windows trust-store persistence

`trusted-devices.json` is written to a synced temporary file first. Windows then tries the standard-library rename path and, when the destination already exists, falls back to removing the old regular file before installing the replacement. This avoids custom Win32 syscall/unsafe glue while still allowing repeated trust-store updates. A crash in the narrow remove-and-rename window can require re-pairing, but the trust store contains identity pins and locators rather than bearer credentials. The loader also rejects symbolic links and unreasonably large trust-store files.
